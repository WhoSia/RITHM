## 2. 실행과 로그의 계약

운영자가 5:1 또는 4:2 배치와 5·10·40기 길이를 지정한다. 서버는 초기 경로의 좌석 배치를 섞고, 초기 5:1이면 A 좌석에서, 4:2면 B 좌석에서 초점 좌석 한 곳을 무작위로 정한다. 매 기 선택 기회는 여섯 좌석에서 독립 균등 추첨한다. 기회 시계는 그룹 생성 때 저장되며, 미래 좌석 순서와 초점 좌석은 일반 화면에 미리 노출되지 않는다. 사전 안내 이력 처치, 초기 배치의 실험적 무작위 배정, 실제 지급은 별도 설계가 필요하다.

정상 순서는 다음과 같다.

1. 2기 선택 확정과 그때의 혼잡을 기록한다.
2. 동일 DB 트랜잭션에서 ±4점 및 경로 항목/별도 정산 표지를 이때 처음 추첨한다. 초점 개인이 2기에 선택한 사람이라면 **그때 확정한 경로**에 귀속한다. 나머지 경우에는 초점 좌석이 그 기에 실제로 이용한 경로에 귀속한다.
3. 단말을 해당 좌석에 넘겨 정산을 열면 서버가 발급 이벤트를 기록한다. 확인 버튼에 연결된 영수증이 맞아야 확인을 기록한다.
4. 확인이 완료된 뒤 3기 화면을 열 수 있다. 확인 뒤 다른 좌석이 먼저 선택하면 그 선택과 초점 좌석의 첫 수정 기회를 분리해 추출한다.

각 이벤트에 순번과 서버 Unix 시각을 남긴다. 순번이 순서의 기준이다. 서버의 발급과 화면 확인 버튼 입력까지를 기록하며, 사람이 읽었는지 또는 어떻게 해석했는지는 로그로 알 수 없다. 화면에서 보수를 보여 주는 로컬 운영 리허설이며, 한 대의 기기에서 좌석에 맞게 넘겨주는 절차에 의존한다.

재시작·새로고침 뒤에도 같은 정산을 표시하고 중복 제출로 추첨하지 않는다. 2기 확정 직후 추첨이 실패하면 트랜잭션 전체를 롤백해 2기 선택 화면에서 다시 진행할 수 있다. 잘못된 좌석·정산 확인 값과 조기 3기 열기를 거부한다. 종료 후 내보내기에는 지급 영수증 토큰이 들어가지 않는다.

## 3. 5기는 화면 검증에 쓰고, 첫 수정률 분석에는 기회 누락을 남긴다

2기 이후 h기까지 초점 좌석이 적어도 한 번 선택 기회를 받을 확률은 1−(5/6)^(h−2)다.

| 종료 시점 | 초점 좌석에서 한 번 이상 관측할 확률 |
|---|---:|
| 3기 | 16.67% |
| 5기 | 42.13% |
| 10기 | 76.74% |
| 40기 | 99.90% |

따라서 5기 리허설의 절반 이상은 초점 좌석 반응이 기록되지 않을 것으로 예상한다. **기회 미도달을 경로 유지로 분류하면 안 된다.** 내보내기에서 첫 수정 기회가 없으면 필드를 null로 두고, 그동안 다른 좌석의 선택을 모두 별도 기록한다. 3기 즉시효과는 3기 기회가 외생적으로 부여된 경우에 해당한다. 10기까지의 첫 수정 효과는 여러 지연 시점을 섞으므로, 3기 즉시효과 대신 쓰려면 기회까지의 지연별 차이를 먼저 확인한다. 40기 혼잡과 자원비용은 모든 배정 집단을 포함하는 결과다.

정산 당시 A 인원은 정산 배정 전에 확정된다. 보수 표시·부호 비교를 그 변수로 층화할 수 있다. 이전 안내 이력 자체의 효과를 연구할 때 그 이력이 혼잡을 바꿨다면, 같은 인원까지 자연 도달한 집단만 골라 비교하는 방식에는 R47의 선택편향 문제가 다시 생길 수 있다.

## 4. 재현과 확인

- Python 표준 라이브러리 테스트 10개. 8개 조합(두 초기 배치 × 두 표시 × 두 부호) 각각 40기, 총 320건의 합성 선택과 672개 이벤트를 재생했다. 같은 DB를 여는 동시 제출, 실패 롤백, 정산 중 서버 재시작, 잘못된 영수증, 기회 미도달, 사후 점유의 감사 실패를 시험했다.
- 두 UI 표시를 하나씩 실행했다. 실제 HTML의 JavaScript 핸들러를 Node의 최소 DOM에서 로컬 HTTP·SQLite에 연결했다. 다시 불러오기, 같은 정산 확인, 다음 기회, JSON 내보내기를 검사했다. 각 로그에서 2기 확정·배정·발급·확인·3기 열기는 순번 5–9였다.
- 이 환경의 Chromium은 시작 단계에서 OS 소켓 제한으로 종료됐다. 실제 브라우저 렌더링과 사람의 시인성·이해도는 별도 검증 대상이다. 합성 경로 선택으로 실제 사람의 처리효과를 추정하지 않는다.
